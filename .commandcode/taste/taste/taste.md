# Taste
- Prefers a plan-first workflow: wants the full set of steps/plan laid out first, and will explicitly give a go-ahead before implementation starts (e.g., "This seems okay, go ahead and execute."). Confidence: 1.0
- Prefers native applications over web browser-based solutions where possible. Confidence: 0.9
- Insists everything live on D:, never C: — projects, SDKs, toolchains, build caches, downloads, and setup all belong on D: because C: has limited space. Emphasizes/repeats this when the assistant probes C:. Confidence: 1.0
- Communicates in terse status reports (e.g., "same", "done", "and on the host it doesnt show any connections") and expects the assistant to diagnose and investigate autonomously rather than ask for more detail; even when the assistant asks pointed clarifying questions (e.g., what the screen showed), the user answers only with the same one-word status. Confidence: 1.0
- Expects the assistant to proactively pull and read diagnostic outputs itself (host log files, phone logcat, wire dumps) and fix from them, rather than asking the user to relay error details ("check logs", "Can you please check the outputs and fix the issue?"). Confidence: 0.85
- Prefers an iterative try-and-report loop: deploys builds to real hardware, tests them hands-on, and reports results/feedback so the assistant tunes the implementation based on real-world usage (e.g., "Okay, start the host, I want to try and then let you know if any recommendations"; after a fix is applied, "then lets run a test"). Confidence: 0.9
- Wants persistent state/memory documentation written to disk (e.g., MEMORY.md in the project) capturing all attempts, fixes, diagnostics, and next steps kept updated after every single change ("after each changes keep updating the memory files, please"), so work resumes cleanly without repeating investigation. Confidence: 0.98
- Prefers background/host apps to have a minimal, unobtrusive UI — tray-only, with no banner/overlay on the display; clicking the tray icon pops up a control window (connected clients, running game, kick-client/close-game/start-stop-host controls), never a console/cmdline window. Confidence: 1.0
- Wants games/apps launched from the mobile client to start silently in the background on the host PC — no popup window, no stolen desktop focus, ideally low graphics/windowed so people at the host machine don't even notice; the stream goes straight to the phone. Confidence: 0.9
- Wants launcher/app lists curated to actual games only — on the host and on the mobile client grid, only games (each with its icon) should show; non-game applications (Discord, Python, Control Panel, etc.) must be filtered out and "the rest" hidden. Confidence: 0.9
- Wants the mobile stream screen fully immersive: no persistent on-screen controls (e.g. no corner exit button); exit/status controls are hidden and revealed by a tap, appearing as a centered overlay that can be dismissed by tapping again. Confidence: 0.9
- Wants the mobile streaming client in landscape fullscreen (locked orientation, no status bars) for the handheld/streaming experience. Confidence: 0.9
- Wants the host app's UI to show live session status — which device is connected and which game is currently running (not just an idle banner); flags it as a defect when the host fails to display the connected mobile device (re-flagged in later testing: "Host app doesnt show any client"). Confidence: 1.0
- Wants streaming bandwidth tuned to be efficient for all games (low-graphics/low-bitrate-friendly settings rather than max quality at any cost). Confidence: 0.6
- Cares about app UI quality/polish — explicitly asks for the client app to be redesigned and the host UI to look good, not just functional. Confidence: 0.7
- Wants icons used everywhere in the UI — tray icon, taskbar icon, banner, window icon, and game list entries — including showing the icon of the currently running game in the host banner (no missing/blank icon slots); explicitly flags when an icon is not visible (e.g. invisible tray icon, or the host app having no taskbar icon at all) and expects it fixed, not skipped. Confidence: 0.97
- Wants the virtual display to exist only on demand: it is enabled/attached only while a client is actively connecting/streaming, and disabled/removed from Windows when idle or when the session ends (explicitly stated: "The virtual display will only enable when client want to connect, rest, it wont be there"). Confidence: 0.9
- Wants a desktop shortcut / one-click launcher to start the host app manually whenever they want, rather than relying on it running automatically. Confidence: 0.8
- Wants launcher/app icons to show the full artwork zoomed out with margin/padding inside the icon mask rather than zoomed-in or cropped — explicitly asked for the Android launcher icon to be zoomed out. Confidence: 0.7
- Wants the host app to expose explicit Start Host / Stop Host controls (tray menu) so hosting can be started/stopped on demand, not just run implicitly at startup. Confidence: 0.8
- Architecture: client discovers alive hosts on the network and initiates the connection with a handshake (announcing its device name). Confidence: 1.0

Explicitly restates/corrects this requirement when the assistant's implementation misses it. Confidence: 1.0
- Wants the client's own screen resolution to drive the virtual display: whenever the client initiates a connection, the host sets the virtual display to exactly the client's resolution (in landscape), and streams that — no other resolution is used. Confidence: 0.9
- Wants a single user-provided icon file (kept in the project folder) used consistently across the whole product — host tray, host popup window, and Android launcher — instead of runtime-drawn or per-context icons. Confidence: 1.0
